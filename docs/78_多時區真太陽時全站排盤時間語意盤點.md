# 78 多時區真太陽時全站排盤時間語意盤點

## 1. 範圍與結論

本文件是第 8A 包的 read-only 設計盤點。第 6、7 包已讓真太陽時頁面能以臺灣上方查詢、裝置目前時間或自訂 IANA 當地時間查詢真太陽時與太陽事件；其中只有來源 A（上方查詢時間、Asia/Taipei）可套用全站。來源 B/C **尚未**、也不應在本包接入全站排盤。

主要結論如下：

1. 節氣 JSON 的 `asia_taipei` 是有 `+08:00` 的真實 instant；節氣比較本身應以 epoch milliseconds 進行。
2. 四柱目前卻把無 offset 的輸入字串用執行環境本機時區轉成 `Date`，再與上述 instant 比較。它只在本機時區等同既有臺灣假設時可靠，不能直接餵海外真太陽 local parts。
3. 日柱、時柱的現行明確規則是輸入鐘面 components、23:00 換日；來源 A 套用真太陽時正是將真太陽 local parts 傳入既有路徑。海外使用時，這份鐘面資料必須與節氣 instant 分開傳遞。
4. 飛星除運盤的西元年份外，均衍生自四柱結果；它不應自行重新解析時區。
5. 金函與登貴各有臺灣／執行環境隱性依賴，必須先建立 adapter。登貴尤其不能將「某 offset 的日出 Date」與「執行機器本機 `new Date(year, …)` 的時辰範圍」直接比較。
6. 奇門 full-cycle timeline 明確以 Asia/Taipei、`+08:00`、臺灣 23:00 有效日建立。未確認海外傳統規則前，不可把動態 offset 取代它；這是第 8B 的 Hard Stop。

本文件不修改公式、資料、`chartTimeState` 或 runtime 行為。

## 2. 三種不可混用的時間概念

### A. 原始 civil local time

使用者輸入或裝置讀取的法定手錶時間。例：

```js
{
  localParts: { year: 2026, month: 8, day: 6, hour: 14, minute: 21, second: 30 },
  timeZone: "America/Los_Angeles",
  utcOffsetMinutes: -420,
}
```

這是選定 IANA 時區中的 civil clock，不是瀏覽器所在時區，也不是座標所自動推導出的時區。

### B. 真實 instant

同一個事件全球唯一的時點。上例在夏令時間選定後為：

```text
2026-08-06T21:21:30.000Z
```

`resolveLocalDateTimeInTimeZone()` 已將此值回傳為 `instant`，並以 earlier/later 保存 DST ambiguous 的選擇。節氣交界、太陽事件的先後、任何跨地比較應使用此語意或其 epoch milliseconds。

### C. 真太陽 local parts

以座標經度與均時差修正後的鐘面年月日時，例如：

```js
{
  year: 2026, month: 8, day: 6, hour: 13, minute: 22, second: 39,
}
```

它不是新的法定 IANA 時區，也不應被重新包裝成「另一個等價的 UTC instant」。第 6 包的 `trueSolarDate` 是 UTC component carrier，僅供以 UTC getter 讀取這些 components；不可把它當作天文事件發生的 instant。

## 3. 現況資料流與 Date 語意

### 3.1 來源 A 相容路徑

`main.js` 的上方查詢框產生無 offset 的 `YYYY-MM-DDTHH:mm[:ss]`。來源 A 真太陽時計算以 `Asia/Taipei` / `480` 及 coordinate 產生 `trueSolarParts`。按「套用」後，現有 `chartTimeState` 保存：

```text
watchDateTimeValue (無 offset 的臺灣手錶字串)
effectiveDateTimeValue (無 offset 的真太陽鐘面字串)
trueSolarResult
location
```

`renderByDateTime(watch)` 再透過 `resolveEffectiveChartDateTimeValue()` 將後續四柱、飛星、金函、奇門全部改餵 `trueSolarParts` 格式化的字串。這是相容契約，並非可泛用的 instant context。

### 3.2 來源 B/C 查詢路徑

* B 以 `new Date()` 取得 instant，再用 `getZonedDateTimeParts()` 取裝置 IANA 的 local parts 與 offset。
* C 以 `resolveLocalDateTimeInTimeZone()` 判定 nonexistent / ambiguous / resolved；選定 earlier/later 後才保留正確 `instant` 和 offset。
* `renderTrueSolarTimeForContext()` 將 local parts 建成 UTC component carrier，呼叫 `calculateTrueSolarTime(..., useUtcComponents: true)`；此作法不依賴瀏覽器本機時區。
* `calculateSolarEvents(..., useUtcComponents: true)` 以指定 local date、座標及 offset 回傳事件 instant 與該 offset 的 parts。

來源 B/C 沒有寫入 `chartTimeState`，也沒有呼叫完整 `renderByDateTime()`，符合目前限制。

### 3.3 已確認的隱性本機時區依賴

| 檔案／位置 | 分類 | 現況 | 風險 |
| --- | --- | --- | --- |
| `solarTerms.parseLocalDateTime()` | 四柱 components + 節氣比較 | `new Date(year, month - 1, …)` 產生 `timeMs` | 無 offset 輸入會以執行環境 TZ 解讀；海外或不同 `TZ` 下節氣邊界會變。 |
| `main.parseDateTimeLocalValue()` / `toLocalDatetimeValue()` | UI、日曆、既有套用 carrier | local Date getters / constructor | 現況假定瀏覽器的本機 local 即上方臺灣時間。 |
| `bazi.getEffectiveDateKeyByTimeMs()` | 每日資訊／三伏 | local getters | term instant 的 effective date 會隨執行環境 TZ 改變。 |
| `jinhanDunType.formatTermLocalDateTime()` | 金函換遁邊界日 | local getters on term instant | `asia_taipei` 節氣 instant 可能被格式成非臺灣 components。 |
| `flyingStars.getLocalYear()` | 運盤 | `new Date(input).getFullYear()` | 無 offset 字串與執行環境綁定。 |
| `guideng.getChineseHourRange()` | 登貴時辰範圍 | local constructor / `setHours` | 與固定 offset 的日出日落 event instants 混用。 |
| `main.formatTermDateTime()`、農曆／日曆顯示 | UI 顯示 | local getters | 顯示可使用明確 formatter；不應成為排盤輸入。 |

以下用途不是多時區問題：`Date.UTC()` 在 `ganzhi.js` 的日柱基準日與純 civil date 加減、`timeZone.js` 的 IANA 解析、`trueSolarTime.js` 的 UTC carrier、`solarEvents.js` 的 offset parts，皆刻意不讀執行機器本機時區。

## 4. 四柱與節氣

`calculateBaziFromSolarTerms(dateTimeString, solarTerms)` 目前接受單一無 offset 字串，所有判斷共用它。

| 柱／判斷 | 現況實際來源 | 交界方式 | 多時區安全建議 |
| --- | --- | --- | --- |
| 年柱 | `parseLocalDateTime` 的 `timeMs` 與立春 `term.timeMs` | epoch 比較，但 query epoch 由本機 TZ 建立 | 節氣先後改用 `civil.instant`；年／月的鐘面年僅作資料索引輔助，不可將海外真太陽字串假裝為臺灣時間。 |
| 月柱 | 同上，12 個「節」與 `getMonthBranch` | epoch 比較 | 同年柱：必須使用真實 instant。 |
| 日柱 | `getDayPillar` 的輸入年月日時 | civil components，`hour >= 23` 時日期 +1 | 沿用已套用真太陽時的規則，使用 `trueSolar.localParts`；23:00 的地方／流派語意仍須確認。 |
| 時柱 | `getHourPillar` 的輸入 hour，並先取日柱 | local components／子時 | 使用 `trueSolar.localParts`，不可由 instant 在臺灣轉出的 hour。 |
| 建除、每日資訊、七十二候 | 由 `termContext`、日柱與 `getEffectiveDateKeyByTimeMs` 衍生 | 混合 instant 與本機 local key | 需在四柱 adapter 一次明確提供「節氣 instant context」與「有效日 local key」，不可各處自行讀 `Date`。 |

日界明確為 23:00，不是 00:00；`ganzhi.js` 與 UI 的子時選取都如此實作。此規則可由目前程式確認，但「海外是否以真太陽 local 23:00 換日」屬命理規則，現有文件只證明來源 A 採真太陽鐘面套用，未提供海外權威定義。

### 概念診斷案例（不改結果）

1. **一般日：** 洛杉磯 2026-08-06 14:21:30、UTC-07:00、34.0522/-118.2437。civil instant 是 `2026-08-06T21:21:30Z`；真太陽 local 仍是 2026-08-06 約 13 時。日／時柱不應被轉成臺灣 2026-08-07 05 時；節氣則應比較 `21:21:30Z`。
2. **立春交界：** 節氣資料的 2026 立春為 `2026-02-03T20:02:09.050Z`（臺灣 `2026-02-04T04:02:09.050+08:00`）。海外輸入在該 instant 前後一秒，年柱／月柱必須隨 instant 切換；若把海外真太陽 local components 當 `+08:00` 字串，會把比較時點平移，可能錯判。

## 5. 九宮飛星

`calculateAllFlyingStarCharts(calendarResult, inputDateTime)` 只有運盤直接解析 `inputDateTime`；其餘四層均使用四柱的衍生結果。

| Layer | 現況來源 | 多時區建議來源 | 風險 |
| --- | --- | --- | --- |
| 運盤 | `new Date(inputDateTime).getFullYear()` | 待確認採 civil local 年或 true-solar local 年；需由 adapter 明確給 year | 無 offset 字串受執行環境 TZ 影響。 |
| 年盤 | `calendarResult.meta.ganzhiYear` / 年柱 | 四柱年柱結果（節氣比較使用 civil instant） | 不應自行取 `Date` 年份。 |
| 月盤 | 年柱、月令 branch | 四柱月柱結果（節氣比較使用 civil instant） | 不應以公曆月替代節令。 |
| 日盤 | 日柱、當前節氣名 | 四柱日柱（true-solar local）與節氣 context（instant） | 需避免日柱與節氣各取不同 context。 |
| 時盤 | 日柱、時柱、當前節氣名 | 四柱時柱（true-solar local）與節氣 context（instant） | 真太陽跨日或跨時辰必須整體一致。 |

`flyingStarViewModel.js` 僅格式化 view model，與時間語意無關。

## 6. 金函玉鏡與登貴

### 6.1 金函玉鏡

* 日盤查表 `getJinhanYujingDayPan(dayPillar, dunType)` 只使用四柱日柱，故應由同一份 true-solar local 日柱供給。
* 黑黃道時 `getJinhanBlackYellowHours(dayPillar)` 只依日柱；目前的當前標記由 `getCurrentChineseHourInfo(dateTimeValue)` 讀無 offset input 的鐘面 hour，應改由 context 的 true-solar local hour adapter 提供。
* `getJinhanDunType()` 的 query effective date 使用既有 23:00 日柱；但冬至／夏至 `formatTermLocalDateTime()` 目前以環境 local getter 取 term instant，而其資料欄名和年度欄位是臺灣基準。第 8B 必須先將 term 的臺灣 civil components 明確讀取，或將換遁規則改為有明確 instant／civil-date contract；不能只傳海外字串。

金函超神接氣是以日還是精確交節時刻切換，及海外真太陽時的適用規則，現有文件仍有待確認項；不得在第 8B 擅自決定。

### 6.2 登貴

`calculateGuiDengForDate()` 已共用 `calculateSolarEvents()`，但正式呼叫仍固定 `utcOffsetMinutes: 480`；`timezone` 僅用於格式化。主畫面又以 `parseDateTimeLocalValue()` 的 local `Date` 當 target date。現況只適合既有臺灣路徑。

安全 adapter 至少要一次帶入：指定的 solar-event civil date、座標、解析後的 offset、IANA 時區，以及太陽事件的完整 instants。日出／日落界線比較必須使用完整 Date/epoch，不能用 UI HH:mm 字串。至於登貴的「日」與時辰該取 civil local 或 true-solar local，現有程式沒有明確規則文字可判定，標記為 **待命理規則確認**；不應假定兩者永遠相同。

## 7. 奇門遁甲：現況與 Hard Stop

奇門 resolver 是目前最高風險模組：

* `qimenResolver.js` 明定 `TAIPEI_OFFSET_MS = 8 * 60 * 60 * 1000`。
* 無 offset query 在 `toTimeMs()` 被直接補為 `+08:00`。
* `getQimenEffectiveDayStart()` 以臺灣 components 計算 23:00 有效日，timeline 字串輸出也是 `+08:00`。
* full-cycle timeline、符頭掃描、置閏窗口與 cache key 都建在此有效日序列。
* `findActualSolarTerm()` 對含 offset 的輸入會做正確的 instant 先後比較；但 `resolveQimenJuFromFullTermCycleDraftEntry()` 再把 hour pillar 轉成 Asia/Taipei components。

因此若直接傳海外 civil instant，節氣名稱雖可依 instant 得到正確比較，時柱與 23:00 有效日仍會是臺灣，不是海外真太陽鐘面。若直接傳海外 true-solar 無 offset字串，resolver 又會把它視為 `+08:00`，造成另一種錯誤。

**Hard Stop：** 在未確認奇門完整置閏 timeline 是否應永遠採臺灣基準，或是否應以使用地的真太陽 23:00 重新定義符頭／有效日之前，禁止讓 B/C 套用奇門，禁止全域動態取代 `+08:00`，也禁止猜測 adapter。第 8B 最多先做隔離式 contract／診斷，不能宣告海外奇門已受支援。

## 9. ChartTimeContext 草案（僅設計）

第 8B 建議建立 immutable pure context，避免一個 `Date` 同時扮演 instant 與 component carrier：

```js
{
  source: "query" | "device" | "custom",
  civil: {
    localParts,                 // 使用者／裝置的法定鐘面
    timeZone,                   // IANA
    utcOffsetMinutes,
    abbreviation,
    instant,                    // 唯一真實 instant Date / epoch
    disambiguation: null | "earlier" | "later",
  },
  location: { latitude, longitude, accuracy: null },
  trueSolar: {
    localParts,                 // 真太陽鐘面，不是 time zone
    correctionSeconds,
    longitudeCorrectionSeconds,
    equationOfTimeSeconds,
    dayOffset,
    result,                     // 現有 calculateTrueSolarTime 結果；carrier 明確只讀 UTC components
  },
  astronomy: {
    comparisonInstant,          // civil.instant 的 alias，供節氣／事件先後比較
    solarEventCivilDate,        // 明確指定 events 要計算哪一個當地日期
  },
  compatibility: {
    taipeiLegacyDateTimeValue,  // 僅來源 A：既有無 offset 的字串
    trueSolarLocalDateTimeValue,// 僅供既有 A compatibility adapter，不等於 instant
  },
}
```

規則：

* `civil.instant` 由 IANA resolver 建立，DST earlier/later 是快照的一部分。
* `trueSolar.localParts` 只能被需要傳統日／時鐘面規則的 adapter 讀取。
* `astronomy.comparisonInstant` 與 `civil.instant` 指同一時點，目的在讓呼叫端不能誤傳 UTC carrier。
* 所有 modules 禁止自行依 IANA 重算 offset；context 建立層是唯一責任點。
* 套用全站時保存 context snapshot；不跟隨裝置現在時間 timer。

## 11. 來源 A 相容策略

第 8B 初期應保留來源 A 的 legacy path，理由是現有所有臺灣 fixtures、`+08:00` 奇門 timeline 和「套用真太陽時」行為均依賴它。新的 context helper 必須先以 A 產生相同的：四柱、飛星、金函、奇門輸入與狀態列，才可考慮讓 A 也走 context adapter。

來源 B/C 不得因為 context 已存在就顯示全站套用按鈕。只有各模組 adapter 的測試與命理規則確認完成後，才可逐項解除限制。

## 12. 第 8B 最小安全拆分

1. **8B-1：pure `createChartTimeContext()`。** 輸入 resolver 結果、座標和 true-solar result；只做 immutable snapshot 與跨 `TZ` 測試，不接 UI／`chartTimeState`。
2. **8B-2：四柱／飛星 adapter。** 將節氣 instant comparison 與 true-solar day/hour components 分開傳遞；先證明 A 完全等價。飛星只讀 adapter 的四柱輸出。
3. **8B-3：金函／登貴 adapter。** 先明確化登貴 event date 與時辰日的規則；以完整 events instant 比較，不能使用 UI 字串。
4. **8B-4：奇門專案決策與 adapter。** 先取得海外置閏 timeline、節氣和 23:00 規則確認。若未確認，維持 B/C unsupported，而非實作猜測版本。
5. **8B-5：整合 UI。** 僅在每個模組完成後讓 B/C 套用；狀態列列出 context snapshot 的 civil 與 true-solar 時間，並驗證所有模組都吃同一 snapshot。

### 8B-1 實作結果

`src/chartTimeContext.js` 現已提供 immutable 的純 `ChartTimeContext` snapshot，但尚未接入 UI、`chartTimeState` 或任何排盤模組。它不保存 `Date`：civil 的全球唯一時點以 `instantMs` 保存，衍生的 `instantIso` 僅供序列化與診斷；civil local 與 true-solar local 則以獨立的 plain parts 保存，後者絕不作為 instant 使用。

`astronomy.comparisonInstantMs` 是 civil instant 的明確語意 alias，供未來節氣與事件比較；`solarEventCivilDateKey` 固定保存 civil local date，避免誤用真太陽跨日 carrier。建立時會 clone 所有 caller 資料，再遞迴 freeze context 與 nested objects。跨 `TZ=Asia/Taipei`、`UTC`、`America/Los_Angeles` 的 child-process probe 已確認固定輸出一致。

本階段仍未接入奇門，亦未解除來源 B/C 的全站排盤限制。

## 13. 第 8B 測試矩陣

* **臺灣回歸：** 來源 A 手錶／真太陽套用前後，既有四柱、飛星、金函、奇門 fixtures 完全不變。
* **洛杉磯一般日：** 夏／冬各一例，分別覆蓋真太陽時跨與不跨時辰；civil instant、真太陽 local 和每盤實際輸入可追蹤。
* **節氣邊界：** 海外輸入在同一節氣 instant 前／後一秒，`TZ=Asia/Taipei`、`UTC`、`America/Los_Angeles` 結果相同。
* **東京、Kathmandu、Lord Howe：** 覆蓋無 DST、UTC+05:45、30 分 DST；Lord Howe 要包括 nonexistent 或 ambiguous。
* **跨日：** 真太陽 local 前一日／次一日，日柱與時柱都使用修正日期；狀態列不可只顯示但某盤仍採 civil 日期。
* **DST ambiguous：** earlier/later 有不同 `civil.instant`，context 必須保留選擇；不得因 true-solar clock 接近而折疊兩者。
* **登貴：** 使用完整日出／日落 instants，UI 的 HH:mm 格式化不得反向影響邊界。
* **模組一致性：** 每盤 debug-only input snapshot 與狀態列可比對，避免 B/C 顯示成功但其中一盤退回 A。
* **奇門：** 在規則確認前只測 A 回歸與 B/C unsupported；確認後才新增海外 23:00／置閏 timeline fixtures。

## 14. 待確認事項與 Hard Stop 重述

1. 海外真太陽時的 23:00 換日是否為正式採用規則。
2. 年／月柱在「真太陽 local 與節氣 instant」同時存在時，是否完全依 instant 切節；程式語意支持此設計，但需命理規則確認後才定案。
3. 金函超神接氣是日級或精確交節時刻，及其海外適用的 civil basis。
4. 登貴事件日期、時辰及日柱各應採 civil local 或 true-solar local 的規則。
5. 奇門 full-cycle/置閏 timeline 是否可從臺灣基準安全映射到海外真太陽 local；未確認前是 Hard Stop。

在上述任一事項未確認前，不得讓 B/C 影響全部排盤，不得將真太陽 local carrier 當 instant，不得將海外字串補成 `+08:00`，也不得為支援海外而改動既有臺灣結果。
