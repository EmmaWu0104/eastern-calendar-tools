## 1. 範圍與結論

本文件是第 8A 包的 read-only 設計盤點。第 6、7 包已讓真太陽時頁面能以臺灣上方查詢、裝置目前時間或自訂 IANA 當地時間查詢真太陽時與太陽事件；其中只有來源 A（上方查詢時間、Asia/Taipei）可套用全站。來源 B/C **尚未**、也不應在本包接入全站排盤。

主要結論如下：

1. 節氣 JSON 的 `asia_taipei` 是有 `+08:00` 的真實 instant；節氣比較本身應以 epoch milliseconds 進行。
2. 四柱目前卻把無 offset 的輸入字串用執行環境本機時區轉成 `Date`，再與上述 instant 比較。它只在本機時區等同既有臺灣假設時可靠，不能直接餵海外真太陽 local parts。
3. 日柱、時柱的現行明確規則是輸入鐘面 components、23:00 換日；來源 A 套用真太陽時正是將真太陽 local parts 傳入既有路徑。海外使用時，這份鐘面資料必須與節氣 instant 分開傳遞。
4. 飛星除運盤的西元年份外，均衍生自四柱結果；它不應自行重新解析時區。
5. 金函與登貴各有臺灣／執行環境隱性依賴，必須先建立 adapter。登貴尤其不能將「某 offset 的日出 Date」與「執行機器本機 `new Date(year, …)` 的時辰範圍」直接比較。
6. 奇門 full-cycle timeline 明確以 Asia/Taipei、`+08:00`、臺灣 23:00 有效日建立。未確認海外傳統規則前，不可把動態 offset 取代它；這是第 8B 的 Hard Stop。

本文件不修改公式、資料、`chartTimeState` 或 runtime 行為。

## 2. 三種不可混用的時間概念

### A. 原始 civil local time

使用者輸入或裝置讀取的法定手錶時間。例：

```js
{
  localParts: { year: 2026, month: 8, day: 6, hour: 14, minute: 21, second: 30 },
  timeZone: "America/Los_Angeles",
  utcOffsetMinutes: -420,
}
```

這是選定 IANA 時區中的 civil clock，不是瀏覽器所在時區，也不是座標所自動推導出的時區。

### B. 真實 instant

同一個事件全球唯一的時點。上例在夏令時間選定後為：

```text
2026-08-06T21:21:30.000Z
```

`resolveLocalDateTimeInTimeZone()` 已將此值回傳為 `instant`，並以 earlier/later 保存 DST ambiguous 的選擇。節氣交界、太陽事件的先後、任何跨地比較應使用此語意或其 epoch milliseconds。

### C. 真太陽 local parts

以座標經度與均時差修正後的鐘面年月日時，例如：

```js
{
  year: 2026, month: 8, day: 6, hour: 13, minute: 22, second: 39,
}
```

它不是新的法定 IANA 時區，也不應被重新包裝成「另一個等價的 UTC instant」。第 6 包的 `trueSolarDate` 是 UTC component carrier，僅供以 UTC getter 讀取這些 components；不可把它當作天文事件發生的 instant。

## 3. 現況資料流與 Date 語意

### 3.1 來源 A 相容路徑

`main.js` 的上方查詢框產生無 offset 的 `YYYY-MM-DDTHH:mm[:ss]`。來源 A 真太陽時計算以 `Asia/Taipei` / `480` 及 coordinate 產生 `trueSolarParts`。按「套用」後，現有 `chartTimeState` 保存：

```text
watchDateTimeValue (無 offset 的臺灣手錶字串)
effectiveDateTimeValue (無 offset 的真太陽鐘面字串)
trueSolarResult
location
```

`renderByDateTime(watch)` 再透過 `resolveEffectiveChartDateTimeValue()` 將後續四柱、飛星、金函、奇門全部改餵 `trueSolarParts` 格式化的字串。這是相容契約，並非可泛用的 instant context。

### 3.2 來源 B/C 查詢路徑

* B 以 `new Date()` 取得 instant，再用 `getZonedDateTimeParts()` 取裝置 IANA 的 local parts 與 offset。
* C 以 `resolveLocalDateTimeInTimeZone()` 判定 nonexistent / ambiguous / resolved；選定 earlier/later 後才保留正確 `instant` 和 offset。
* `renderTrueSolarTimeForContext()` 將 local parts 建成 UTC component carrier，呼叫 `calculateTrueSolarTime(..., useUtcComponents: true)`；此作法不依賴瀏覽器本機時區。
* `calculateSolarEvents(..., useUtcComponents: true)` 以指定 local date、座標及 offset 回傳事件 instant 與該 offset 的 parts。

來源 B/C 沒有寫入 `chartTimeState`，也沒有呼叫完整 `renderByDateTime()`，符合目前限制。

### 3.3 已確認的隱性本機時區依賴

| 檔案／位置 | 分類 | 現況 | 風險 |
| --- | --- | --- | --- |
| `solarTerms.parseLocalDateTime()` | 四柱 components + 節氣比較 | `new Date(year, month - 1, …)` 產生 `timeMs` | 無 offset 輸入會以執行環境 TZ 解讀；海外或不同 `TZ` 下節氣邊界會變。 |
| `main.parseDateTimeLocalValue()` / `toLocalDatetimeValue()` | UI、日曆、既有套用 carrier | local Date getters / constructor | 現況假定瀏覽器的本機 local 即上方臺灣時間。 |
| `bazi.getEffectiveDateKeyByTimeMs()` | 每日資訊／三伏 | local getters | term instant 的 effective date 會隨執行環境 TZ 改變。 |
| `jinhanDunType.formatTermLocalDateTime()` | 金函換遁邊界日 | local getters on term instant | `asia_taipei` 節氣 instant 可能被格式成非臺灣 components。 |
| `flyingStars.getLocalYear()` | 運盤 | `new Date(input).getFullYear()` | 無 offset 字串與執行環境綁定。 |
| `guideng.getChineseHourRange()` | 登貴時辰範圍 | local constructor / `setHours` | 與固定 offset 的日出日落 event instants 混用。 |
| `main.formatTermDateTime()`、農曆／日曆顯示 | UI 顯示 | local getters | 顯示可使用明確 formatter；不應成為排盤輸入。 |

以下用途不是多時區問題：`Date.UTC()` 在 `ganzhi.js` 的日柱基準日與純 civil date 加減、`timeZone.js` 的 IANA 解析、`trueSolarTime.js` 的 UTC carrier、`solarEvents.js` 的 offset parts，皆刻意不讀執行機器本機時區。

## 4. 四柱與節氣

`calculateBaziFromSolarTerms(dateTimeString, solarTerms)` 目前接受單一無 offset 字串，所有判斷共用它。

| 柱／判斷 | 現況實際來源 | 交界方式 | 多時區安全建議 |
| --- | --- | --- | --- |
| 年柱 | `parseLocalDateTime` 的 `timeMs` 與立春 `term.timeMs` | epoch 比較，但 query epoch 由本機 TZ 建立 | 節氣先後改用 `civil.instant`；年／月的鐘面年僅作資料索引輔助，不可將海外真太陽字串假裝為臺灣時間。 |
| 月柱 | 同上，12 個「節」與 `getMonthBranch` | epoch 比較 | 同年柱：必須使用真實 instant。 |
| 日柱 | `getDayPillar` 的輸入年月日時 | civil components，`hour >= 23` 時日期 +1 | 沿用已套用真太陽時的規則，使用 `trueSolar.localParts`；23:00 的地方／流派語意仍須確認。 |
| 時柱 | `getHourPillar` 的輸入 hour，並先取日柱 | local components／子時 | 使用 `trueSolar.localParts`，不可由 instant 在臺灣轉出的 hour。 |
| 建除、每日資訊、七十二候 | 由 `termContext`、日柱與 `getEffectiveDateKeyByTimeMs` 衍生 | 混合 instant 與本機 local key | 需在四柱 adapter 一次明確提供「節氣 instant context」與「有效日 local key」，不可各處自行讀 `Date`。 |

日界明確為 23:00，不是 00:00；`ganzhi.js` 與 UI 的子時選取都如此實作。此規則可由目前程式確認，但「海外是否以真太陽 local 23:00 換日」屬命理規則，現有文件只證明來源 A 採真太陽鐘面套用，未提供海外權威定義。

### 概念診斷案例（不改結果）

1. **一般日：** 洛杉磯 2026-08-06 14:21:30、UTC-07:00、34.0522/-118.2437。civil instant 是 `2026-08-06T21:21:30Z`；真太陽 local 仍是 2026-08-06 約 13 時。日／時柱不應被轉成臺灣 2026-08-07 05 時；節氣則應比較 `21:21:30Z`。
2. **立春交界：** 節氣資料的 2026 立春為 `2026-02-03T20:02:09.050Z`（臺灣 `2026-02-04T04:02:09.050+08:00`）。海外輸入在該 instant 前後一秒，年柱／月柱必須隨 instant 切換；若把海外真太陽 local components 當 `+08:00` 字串，會把比較時點平移，可能錯判。

## 6. 金函玉鏡與登貴

### 6.1 金函玉鏡

* 日盤查表 `getJinhanYujingDayPan(dayPillar, dunType)` 只使用四柱日柱，故應由同一份 true-solar local 日柱供給。
* 黑黃道時 `getJinhanBlackYellowHours(dayPillar)` 只依日柱；目前的當前標記由 `getCurrentChineseHourInfo(dateTimeValue)` 讀無 offset input 的鐘面 hour，應改由 context 的 true-solar local hour adapter 提供。
* `getJinhanDunType()` 的 query effective date 使用既有 23:00 日柱；但冬至／夏至 `formatTermLocalDateTime()` 目前以環境 local getter 取 term instant，而其資料欄名和年度欄位是臺灣基準。第 8B 必須先將 term 的臺灣 civil components 明確讀取，或將換遁規則改為有明確 instant／civil-date contract；不能只傳海外字串。

金函超神接氣是以日還是精確交節時刻切換，及海外真太陽時的適用規則，現有文件仍有待確認項；不得在第 8B 擅自決定。

### 6.2 登貴

`calculateGuiDengForDate()` 已共用 `calculateSolarEvents()`，但正式呼叫仍固定 `utcOffsetMinutes: 480`；`timezone` 僅用於格式化。主畫面又以 `parseDateTimeLocalValue()` 的 local `Date` 當 target date。現況只適合既有臺灣路徑。

安全 adapter 至少要一次帶入：指定的 solar-event civil date、座標、解析後的 offset、IANA 時區，以及太陽事件的完整 instants。日出／日落界線比較必須使用完整 Date/epoch，不能用 UI HH:mm 字串。至於登貴的「日」與時辰該取 civil local 或 true-solar local，現有程式沒有明確規則文字可判定，標記為 **待命理規則確認**；不應假定兩者永遠相同。

## 7. 奇門遁甲：現況與 Hard Stop

奇門 resolver 是目前最高風險模組：

* `qimenResolver.js` 明定 `TAIPEI_OFFSET_MS = 8 * 60 * 60 * 1000`。
* 無 offset query 在 `toTimeMs()` 被直接補為 `+08:00`。
* `getQimenEffectiveDayStart()` 以臺灣 components 計算 23:00 有效日，timeline 字串輸出也是 `+08:00`。
* full-cycle timeline、符頭掃描、置閏窗口與 cache key 都建在此有效日序列。
* `findActualSolarTerm()` 對含 offset 的輸入會做正確的 instant 先後比較；但 `resolveQimenJuFromFullTermCycleDraftEntry()` 再把 hour pillar 轉成 Asia/Taipei components。

因此若直接傳海外 civil instant，節氣名稱雖可依 instant 得到正確比較，時柱與 23:00 有效日仍會是臺灣，不是海外真太陽鐘面。若直接傳海外 true-solar 無 offset字串，resolver 又會把它視為 `+08:00`，造成另一種錯誤。

**Hard Stop：** 在未確認奇門完整置閏 timeline 是否應永遠採臺灣基準，或是否應以使用地的真太陽 23:00 重新定義符頭／有效日之前，禁止讓 B/C 套用奇門，禁止全域動態取代 `+08:00`，也禁止猜測 adapter。第 8B 最多先做隔離式 contract／診斷，不能宣告海外奇門已受支援。

## 9. ChartTimeContext 草案（僅設計）

第 8B 建議建立 immutable pure context，避免一個 `Date` 同時扮演 instant 與 component carrier：

```js
{
  source: "query" | "device" | "custom",
  civil: {
    localParts,                 // 使用者／裝置的法定鐘面
    timeZone,                   // IANA
    utcOffsetMinutes,
    abbreviation,
    instant,                    // 唯一真實 instant Date / epoch
    disambiguation: null | "earlier" | "later",
  },
  location: { latitude, longitude, accuracy: null },
  trueSolar: {
    localParts,                 // 真太陽鐘面，不是 time zone
    correctionSeconds,
    longitudeCorrectionSeconds,
    equationOfTimeSeconds,
    dayOffset,
    result,                     // 現有 calculateTrueSolarTime 結果；carrier 明確只讀 UTC components
  },
  astronomy: {
    comparisonInstant,          // civil.instant 的 alias，供節氣／事件先後比較
    solarEventCivilDate,        // 明確指定 events 要計算哪一個當地日期
  },
  compatibility: {
    taipeiLegacyDateTimeValue,  // 僅來源 A：既有無 offset 的字串
    trueSolarLocalDateTimeValue,// 僅供既有 A compatibility adapter，不等於 instant
  },
}
```

規則：

* `civil.instant` 由 IANA resolver 建立，DST earlier/later 是快照的一部分。
* `trueSolar.localParts` 只能被需要傳統日／時鐘面規則的 adapter 讀取。
* `astronomy.comparisonInstant` 與 `civil.instant` 指同一時點，目的在讓呼叫端不能誤傳 UTC carrier。

* 套用全站時保存 context snapshot；不跟隨裝置現在時間 timer。

### 8B-1 實作結果

## 13. 第 8B 測試矩陣

* **臺灣回歸：** 來源 A 手錶／真太陽套用前後，既有四柱、飛星、金函、奇門 fixtures 完全不變。
* **洛杉磯一般日：** 夏／冬各一例，分別覆蓋真太陽時跨與不跨時辰；civil instant、真太陽 local 和每盤實際輸入可追蹤。
* **節氣邊界：** 海外輸入在同一節氣 instant 前／後一秒，`TZ=Asia/Taipei`、`UTC`、`America/Los_Angeles` 結果相同。
* **東京、Kathmandu、Lord Howe：** 覆蓋無 DST、UTC+05:45、30 分 DST；Lord Howe 要包括 nonexistent 或 ambiguous。
* **跨日：** 真太陽 local 前一日／次一日，日柱與時柱都使用修正日期；狀態列不可只顯示但某盤仍採 civil 日期。
* **DST ambiguous：** earlier/later 有不同 `civil.instant`，context 必須保留選擇；不得因 true-solar clock 接近而折疊兩者。
* **登貴：** 使用完整日出／日落 instants，UI 的 HH:mm 格式化不得反向影響邊界。
* **模組一致性：** 每盤 debug-only input snapshot 與狀態列可比對，避免 B/C 顯示成功但其中一盤退回 A。
* **奇門：** 在規則確認前只測 A 回歸與 B/C unsupported；確認後才新增海外 23:00／置閏 timeline fixtures。

## 14. 待確認事項與 Hard Stop 重述

1. 海外真太陽時的 23:00 換日是否為正式採用規則。
2. 年／月柱在「真太陽 local 與節氣 instant」同時存在時，是否完全依 instant 切節；程式語意支持此設計，但需命理規則確認後才定案。
3. 金函超神接氣是日級或精確交節時刻，及其海外適用的 civil basis。
4. 登貴事件日期、時辰及日柱各應採 civil local 或 true-solar local 的規則。
5. 奇門 full-cycle/置閏 timeline 是否可從臺灣基準安全映射到海外真太陽 local；未確認前是 Hard Stop。

在上述任一事項未確認前，不得讓 B/C 影響全部排盤，不得將真太陽 local carrier 當 instant，不得將海外字串補成 `+08:00`，也不得為支援海外而改動既有臺灣結果。

## 15. 8B-2A 四柱 adapter

`src/baziChartTimeAdapter.js` 保持純核心，只接收已驗證的 immutable `ChartTimeContext` 與已正規化的節氣陣列；正式 runtime 由 `main.js` orchestration helper 接線，但 adapter 本身不解析 IANA 時區、不計算真太陽時，也不把真太陽鐘面轉回 instant。

* 年柱與月柱一律以 `context.astronomy.comparisonInstantMs`（必須等於 `civil.instantMs`）和 `term.timeMs` 作 epoch milliseconds 比較；交節瞬間沿用既有 `>=`，故瞬間即切入新柱。
* watch 模式的日／時柱使用 `civil.localParts`；true-solar 模式使用 `trueSolar.localParts`。兩者均沿用既有地方鐘面 23:00 換日。
* `bazi.js` 僅抽出共用 pure helper：legacy `calculateBaziFromSolarTerms(dateTimeString, solarTerms)` 的 export、輸入與既有行為均保留。新 separated-time 入口讓 adapter 不需複製年／月／日／時柱公式。
* 來源 A 的一般 watch 與真太陽 carrier fixture 均與 legacy 四柱、節氣與 meta 相符。已確認的邊界診斷：2026 立春 instant（`2026-02-03T20:02:09.050Z`）在臺灣的真太陽校正約為 -461 秒；legacy 將其 `03:54:27` carrier 當臺灣無 offset 字串，仍落在立春前，而 adapter 依 civil instant 在瞬間切入丙午年。這是既有語意差異，runtime 尚未改動。
* 測試涵蓋 Tokyo、洛杉磯夏令時間、立春與月節的前／瞬間／後、LA DST earlier/later（人工 term 放在兩 instant 中間）、Kathmandu、Lord Howe，以及真太陽前／次日。固定 fixture 在 `TZ=Asia/Taipei`、`UTC`、`America/Los_Angeles` 子程序的 JSON 輸出相同。

奇門仍是 Hard Stop，尚未處理。

## 16. 8B-2B 四柱 runtime 接入結果

正式 runtime 已在 `main.js` 建立 `createCurrentTrueSolarChartContext()` orchestration helper。正式四柱只接來源 A（上方 Asia/Taipei 查詢）；來源 B（裝置目前時間與 IANA 時區）與來源 C（自訂當地時間、含已選 DST earlier/later）仍沿用既有 resolver、`calculateTrueSolarTime()` 與 `createTrueSolarChartTimeContext()` 作為獨立查詢，不會覆寫正式 context；不從 true-solar local 反推 instant。

watch path 保持 `calculateBaziFromSolarTerms()`，並以 `currentWatchBaziResult`（同時保留 legacy `currentCalendarResult`）作為 watch 下游 snapshot。true-solar mode 建立獨立 `currentTrueSolarChartContext`／`currentTrueSolarBaziResult`，以 adapter 結果覆蓋四柱與節氣區塊，不覆寫 shared watch result；8B-3B 起飛星改讀正式模式對應的 ChartTimeContext，金函、登貴與奇門仍讀 watch 輸入。

true-solar context 尚未就緒（無座標、無效時區、nonexistent local time、ambiguous 尚未選、計算或 validation 失敗）時，四柱區塊顯示「尚未取得完整真太陽時資料」，不 fallback 成 watch 四柱。切回 watch 會立即恢復 legacy 四柱；真太陽查詢設定不需清除。

true-solar 四柱的節氣判斷仍用 civil instant；節氣顯示則以該 term instant 搭配 context 的 IANA 時區動態格式化，故 Tokyo 顯示 UTC+09、LA 依 term 日期顯示夏／冬 UTC-07／UTC-08。watch 的原有 Asia/Taipei formatter 不變。2026 立春 before/exact/after 1ms 已驗證 exact 即切新年柱；legacy watch 行為未改。真太陽跨日案例的日／時柱跟隨 true-solar local，四柱區塊與上方農曆日期若不同，仍是後續 UX 待辦。

本包未將存在 legacy Date／Taipei effective-date 依賴的每日附屬資訊偽裝成 true-solar；該類內容暫留 watch/legacy 顯示範圍。奇門仍維持 Hard Stop，尚未接入海外真太陽規則。

## 17. 8B-2B-R2 共用上方查詢時間與雙時間顯示

正式真太陽時四柱以頁面上方 `#datetime` 的查詢字串作為唯一 watch/civil 輸入，固定解讀為 `Asia/Taipei`（UTC+08），再以目前座標計算 true-solar local。切換手錶／真太陽時模式不會改寫上方查詢時間，也不會以來源 B/C 的欄位作為正式四柱輸入；切回手錶時間立即回到既有 watch 四柱。

真太陽時模式的上方狀態固定分行顯示手錶時間（含秒）、真太陽時（含秒）及時區。來源 B/C 仍保留於真太陽時區塊，可獨立查詢裝置或自訂時間；後續若要將其正式納入四柱，仍需另行定義全站時間語意與 IANA/節氣顯示策略。

## 18. 8B-2B-R3 排盤時間來源 UX

頁面上方 `#datetime` 的正式名稱為「排盤時間」，並以既有 `isAutoNowMode` 顯示兩種操作狀態：`● 跟隨現在時間` 或 `○ 手動查詢時間`。手動輸入、月曆日期或時辰選取會沿用既有 `pauseAutoNowMode()`；「現在時間」按鈕沿用 `startAutoNowMode()` 恢復更新，不新增第二份狀態或 timer。watch／true-solar 模式與 tab 切換不會改變 auto/manual 狀態。

真太陽時來源 A 以「上方排盤時間／正式排盤來源」標示；來源 B/C 明確標為「僅換算查詢」。Source A 顯示的來源時間即上方排盤時間，正式四柱仍只使用該 shared civil query time；B/C 不會修改正式排盤時間或四柱 context。本包不引入網路校時，現在時間仍來自執行裝置的 JavaScript `new Date()`。

## 19. 8B-2B-R3 後正式四柱時間同步 blocking bug 修正

回溯發現 `toLocalDatetimeValue()` 原本只輸出到分鐘，auto-now 會把 `#datetime` 的秒數截成 `00`；另外既有 1 秒真太陽時 clock refresh 只更新查詢面板，沒有重建正式 `currentTrueSolarChartContext`／`currentTrueSolarBaziResult`，所以 true-solar 狀態列可能停在進入模式時的快照。

修正後，正式 authority 仍是當下 `#datetime.value`：local datetime formatter 保留 `YYYY-MM-DDTHH:mm:ss`，top query 變更會先 invalidate 舊 formal context；既有 clock timer 在 auto-now 下同步 top query，再由 `renderFormalTrueSolarChartTime()` 重新建立 context 與四柱結果。手動模式停止該同步，來源 B/C 仍只更新獨立換算面板，不污染正式四柱。未新增 timer，也未修改 adapter、ChartTimeContext schema、真太陽時公式、節氣資料或其他盤面。

## 20. 8B-2B-R3/R4 正式排盤／B-C 查詢來源隔離

後續回溯發現正式 auto-now refresh 曾透過共用 `renderTrueSolarTimeForContext()` 寫入查詢面板，造成 Source C／B 短暫顯示後被 Source A 覆蓋。現已抽出無 DOM side effect 的 `resolveTrueSolarTimeCalculation()`；正式路徑只建立 formal context、四柱結果與正式狀態列，查詢路徑才更新來源標籤、查詢結果、query status 與 solar events。

clock timer 依來源分工：Source QUERY 可跟隨上方排盤時間、Source DEVICE 更新裝置面板、Source CUSTOM 不做自動 query refresh；正式四柱仍獨立讀上方 `#datetime`。B/C radio、固定時間與 query result 不會因 formal refresh 或 tab/mode 切換被改寫。未新增 timer，亦未修改 adapter、ChartTimeContext schema、公式或其他盤面。

## 21. 8B-2C 真太陽四柱每日附屬資訊補齊

先前 true-solar 四柱在 `renderTrueSolarBaziResult()` 內無條件呼叫 `clearPillarExtraPanel()`；資料本身並未消失，而是為了避免混用 civil date 而暫時隱藏。現在 separated-time core 接受可驗證的 `effectiveDayDateKey`，由 `clockLocalParts` 的既有 23:00 規則推導並由 adapter 明確傳入；若呼叫端傳入不一致的 key 會拒絕。legacy `calculateBaziFromSolarTerms()` 的日期路徑保持不變。

真太陽日層級以 `context.trueSolar.localParts` 為唯一鐘面來源。建除、黃道／黑道、衣著、衝煞、歲破、天赦與寶義合值法均從真太陽月支／日柱或同一 effective day 產生；三伏的查詢日期使用真太陽 `effectiveDayDateKey`，夏至／立秋仍由 solar-term instant 產生日期基準。正式 Asia/Taipei compatibility path 的四離／四絕仍以 upcoming term instant 的 Taipei effective day 與真太陽 effective day 比較；海外時區的 seasonal marker 在規則未定義前由 UI safe model 保持 hidden/null。

真太陽結果現在以同一份 safe daily-info model 重畫原有 pillar extra panel，並以有效日 key 更新上方日期摘要；時辰切換只重畫四柱，不會清除日柱附屬區。solar-term day panel 與農曆 CWA civil-date contract 仍維持既有相容語意；8B-3B 起飛星跟隨正式 true-solar context，金函、登貴與奇門仍維持 watch 輸入，真太陽結果也沒有寫回 shared `currentCalendarResult`。新增測試涵蓋 23:00 前／瞬間、前／次日、三伏、建除／黃道、衣著／衝煞、seasonal marker、watch 回歸、面板接線與跨 `TZ` process 一致性。

## 22. 8B-2C auto-now 時辰交界四柱優先更新

人工驗證發現 top `#datetime` 的秒數已每秒變動，但時辰交界的 watch 四柱仍可能延遲十幾秒。量測程式路徑後確認：auto-now 的完整 downstream refresh 原本以 30 秒 timer 觸發，且 `renderByDateTime()` 會等待 `renderJinhanYujing()`；後者再等待 GuiDeng／solar-events 計算完成。Bazi、GuiDeng、奇門核心本身的直接量測都只有毫秒級，因此根因是完整非同步盤面隊列與時序，而非時辰規則或公式變慢。

現在既有 1 秒 auto-now clock 在 solar terms 已載入時，會先走無 `await` 的 `refreshBaziForCurrentChartTime()`：watch 直接重算並重畫四柱與飛星，真太陽模式則重建 formal context／adapter 結果並重畫正式飛星；手動或一般 query 變更也在進入 `isCalculating` queue 前先做同一個輕量更新。金函、登貴、奇門仍由原本完整 render 路徑處理，且維持 watch 輸入；飛星不再被 legacy full-render writer 覆寫。

每次時間變更都遞增 `latestBaziRenderRequestId`。完整 render 與 Jinhan await 前後均檢查 request id；舊請求、舊 pending 值或舊錯誤不能覆寫最新四柱，只有最新請求可提交 downstream 結果。未新增 timer，也未修改 ChartTimeContext schema、adapter／真太陽時／節氣／每日資訊規則或任何公式。

測試補上 watch 與真太陽 local 的 09:00:00 時辰交界、23:00:00 換日／日柱／時柱及 daily panel 保留；另驗證 rapid manual input 只留下最新請求、B/C 查詢隔離、downstream 仍採 watch，以及既有兩個 timer 數量不變。

## 23. 8B-3A 九宮飛星 ChartTimeContext pure adapter

## 26. 8B-4A 金函玉鏡真太陽時時間語意定案

本包只新增 `src/jinhanChartTimeAdapter.js` 純核心與 `src/jinhanDunType.js` 的 local-parts boundary helper；沒有接 UI、`main.js` 或正式 runtime。既有 `getJinhanDunType()` 的 v1 authority、120 盤資料與手動覆寫概念均保留。

### 26.1 v1 陰陽遁規則

金函超神接氣 v1 是本工具的既有 authority：冬至的目標遁為陽遁，夏至的目標遁為陰遁；換遁只看日干甲，不看地支。交節日干的完整 mapping 固定如下：

| 交節日干 | mode | 甲日換遁相對交節有效日 |
| --- | --- | ---: |
| 甲 | 正授 | 0 |
| 乙、丙、丁、戊 | 接氣 | -1、-2、-3、-4 |
| 己、庚、辛、壬、癸 | 超神 | +5、+4、+3、+2、+1 |

23:00 是干支有效日界；換遁甲日也從該甲日之前一個民用日期的 23:00:00 起生效，不是 00:00。節氣的 `term.timeMs` 仍是全球唯一 astronomical instant，但不代表該 instant 一到就直接切換陰陽遁；它先轉成模式 local clock，依 23:00 取得交節所屬日與日干，再依上表取得真正 switch day。

### 26.2 watch 與 true-solar authority

* watch query day 使用 `context.civil.localParts` 的 23:00 effective day。
* true-solar query day 使用 `context.trueSolar.localParts` 的 23:00 effective day。
* watch 的節氣 local clock 是 `term.timeMs` 經 `context.civil.timeZone` 轉出的 civil local。
* true-solar 的節氣 local clock 以同一座標、同一 legal timezone/offset basis，對該 `term.timeMs` 重新計算均時差與經度修正；不可重用 query 的 `context.trueSolar.localParts` 或 query EOT。
* 同一 astronomical instant 在 watch／true-solar 可能落在不同 23:00 日界，因而得到不同交節日干、正授／接氣／超神、switch day 與 dun type。這是本工具真太陽時模式的產品時間語意定案，不聲稱是古籍已明文規定的全球 IANA 時區規則。

日盤直接使用同一模式的 Bazi `result.dayPillar`；黑黃道十二時與 current-hour 只使用同一模式 local hour；喜神、財神、陰貴神、陽貴神只從已查得日盤的 `pan.meta` 產生，不另做時間計算。金函的「貴人 placement」不等於登貴時間窗，登貴本包未處理。

### 26.3 pure contract、限制與驗證

adapter 提供 `calculateJinhanFromChartTimeContext()`、`createJinhanCalculationInput()`、`resolveJinhanDunTypeFromChartTimeContext()`、`getJinhanClockLocalParts()`、`getJinhanTermLocalParts()`、`validateJinhanChartTimeInput()` 與 `formatJinhanChartTimeDebug()`。缺少節氣資料時回傳 `unsupported`，不 fallback 到 watch；不解析 DOM、不寫 storage、不 import Guideng／solarEvents／`main.js`，也不處理登貴。

測試包含 157 個 adapter cases：正授、接氣、超神與 23:00 前／瞬間／後、watch／true-solar query/term divergence、January previous-winter interval、Tokyo、Los Angeles summer/winter、Kathmandu、Lord Howe，以及 `TZ=Asia/Taipei`／`UTC`／`America/Los_Angeles` process probe 完全一致。奇門仍是 Hard Stop；本包未接 runtime。

## 28. 8B-5A 登貴 ChartTimeContext pure adapter 與真太陽時時間語意定案

本包只建立登貴的 pure adapter，不接 `main.js`、DOM、UI 或正式 runtime；既有 runtime 因而仍維持 watch／query 的 legacy 輸入。新增 `src/guidengChartTimeAdapter.js`，並在 `src/guideng.js` 抽出可指定 civil local date 的時辰 wall-clock helper，以及接受已解析 actual ranges 的 `calculateGuiDengWithSunTimesForHourRanges()`，讓 adapter 重用原有登貴 mapping、時辰分段與日出／日落交集規則。`src/solarEvents.js` 的公式與既有 API 沒有修改，README 也沒有修改。

### 28.1 時間 authority 與 23:00 有效日

登貴 adapter 的時間語意明確採本工具的 `ChartTimeContext` contract：

* watch 模式的鐘面與 23:00 effective day 使用 `context.civil.localParts`。
* true-solar 模式的鐘面與 23:00 effective day 使用 `context.trueSolar.localParts`；真太陽 local clock 不會再被轉成 `Date` 或另一個 instant。
* 查詢 instant 永遠是 `context.civil.instantMs`。同一 query instant 下，watch／true-solar 可以因 local clock 跨 23:00 而得到不同日柱、日干、effective day 與時辰語意。
* day pillar／day stem 完全取自呼叫端已完成的 `baziResult.dayPillar`，不重新解析 raw datetime 或重算 Bazi；月將完全沿用 `baziResult.currentTerm` 與既有 `getMonthGeneralBySolarTermName()`。

因此 22:59:59、23:00:00、23:00:01 會依模式 local clock 依序套用有效日規則；這個換日不會偷偷改變太陽事件查詢日期。它是本工具真太陽時模式的產品時間語意，不宣稱是古籍已明文規定的全球 IANA 時區規則。

### 28.2 太陽事件、相位與登貴結果

日出／日落查詢日期唯一取自 `context.astronomy.solarEventCivilDateKey`（亦即 civil local date），並同時查詢該 civil date 與下一個 civil date 的實際事件 instant。civil 午夜會改變事件日期；true-solar 23:00 跨日不會改變事件日期。輸出保留 `sunriseInstantMs`、`sunsetInstantMs`、`nextSunriseInstantMs`，不以 local wall-clock 反推事件。

相位邊界固定為：`query < sunrise` 是 `before-sunrise`；`sunrise <= query < sunset` 是 `daytime`（日出 exact 歸白天）；`query >= sunset` 是 `after-sunset`（日落 exact 歸日落後／夜間）。`daytime` 啟用陽貴，其餘兩相位啟用陰貴。既有 `calculateGuiDengHourBranches()`、日出／日落可用區間與 entries mapping 沒有複製或改寫；新增 helper 只避免 host process timezone 的 `Date#getHours()` 影響純核心。輸出也提供 `dengGuiBranches`、day pillar、day stem、current term、month general 與 locale-independent debug snapshot。

watch context 沒有 location 時沿用既有 `DEFAULT_GUIDENG_LOCATION`（Taipei legacy default）；true-solar context 必須帶合法 location，不能 fallback 到 watch。這個 default 是相容性 fallback，不會把 true-solar local 當作事件 instant。

true-solar Chinese-hour boundary 不會把 `context.trueSolar.localParts` 直接交給 IANA resolver 當作答案。adapter 先以該 legal timezone wall-clock 建立 bounded initial guess，再反覆以 `getZonedDateTimeParts()` 取得實際 civil local／offset，呼叫既有 `calculateTrueSolarTime()`，把算出的 true-solar clock 與目標 `HH:00:00` 的差值回饋到 guess；兩個 boundary 各自求解至 1 秒內，才交給 Guideng intersection。這是 clock-boundary inversion：它求出「該 true-solar clock 對應的 actual instant」，不是宣告 true-solar local 是另一個 timezone 或 alternate instant。true-solar 23:00 子時的 end 會以次日 01:00 再求一次，沒有假定 duration 是固定兩個 civil 小時；watch path 仍直接沿用 civil local helper。

### 28.3 多時區、DST 限制與測試

非 DST transition 日期已驗證 Taiwan、Tokyo、Los Angeles 夏／冬、Kathmandu、Lord Howe；同一 input 在 `TZ=Asia/Taipei`、`UTC`、`America/Los_Angeles` process probe 產生相同結果。現有 `calculateSolarEvents()` 是單一 fixed offset contract，無法在 DST transition 日宣稱精確；adapter 會偵測當日或次日 offset 改變並回傳 `unsupported`，不製造假 sunrise／sunset。DST transition coverage 是 Hard Stop，並已以 Los Angeles 2026-03-08 regression 鎖定。

adapter API 包含 `calculateGuiDengFromChartTimeContext()`、`createGuiDengCalculationInput()`、`resolveTrueSolarLocalDateTimeToInstant()`、`getGuiDengClockLocalParts()`、`getGuiDengDayPillar()`、`getGuiDengDayStem()`、`getGuiDengMonthGeneral()`、`getGuiDengSolarEventDateKey()`、`resolveGuiDengSolarEventPhase()`、`validateGuiDengChartTimeInput()` 與 `formatGuiDengChartTimeDebug()`。測試新增 156 cases，涵蓋合法／不合法 context、watch legacy range、zero／positive／negative correction、true-solar 23:00／01:00、兩 boundary reverse-check（誤差 <=1 秒）、naive IANA mapping 排除、civil midnight、watch/true-solar divergence、default location、Tokyo、Los Angeles 夏／冬、Kathmandu、Lord Howe、DST unsupported、process TZ 一致性、static no-DOM/no-main/no-storage/no-network、無 duplicated EOT／solar-events／Bazi formula／mapping，以及 immutable/non-mutation contract。

## 29. 8B-5B 登貴 ChartTimeContext 正式 runtime 接線與真太陽時顯示一致性

8B-5B 將正式登貴 runtime 接到 `calculateGuiDengFromChartTimeContext()`。手錶時間模式使用目前的 watch `ChartTimeContext` 與 `currentWatchBaziResult`；真太陽時模式只使用 `currentTrueSolarChartContext` 與 `currentTrueSolarBaziResult`，不再以 `currentCalendarResult` 或 legacy `getGuiDengForCalendarResult()` 作為真太陽時來源。legacy helper 仍保留給相容性測試與尚未遷移的舊呼叫者，但正式 Jinhan／登貴路徑不會經過它。

金函核心與登貴仍共用同一個 `latestBaziRenderRequestId` generation。每次 render 先由既有 Jinhan snapshot 寫入盤面與黑黃道時辰列，再 fire-and-guard 非同步登貴計算；GuiDeng await 不會進入四柱／飛星的 lightweight 1 秒 critical path。await 前、await 後、display model 建立後與 DOM commit 前都檢查 generation，舊請求不能覆寫最新 snapshot。座標變更、模式切換與完整查詢會即時重跑同一條接線；來源 B/C 仍只作獨立換算查詢，不會改寫正式登貴。

adapter 的 `queryInstantMs` 仍是 civil／手錶的實際 instant；日出、日落、下一次日出與 true-solar Chinese-hour boundary 的 actual instants 只作計算與交集比較。23:00 有效日、日干、月將、時辰分支與 activeGuiRen 均由目前模式的 adapter snapshot 決定；真太陽時的時辰邊界仍以既有 inversion 求得 actual instant，沒有把真太陽 wall clock 偽裝成 `Date`。

正式 UI 透過純 `src/chartClockDisplay.js` 建立 display model。手錶時間將每一個 actual event instant 以其 IANA civil local clock 顯示；真太陽時則對 sunrise、sunset、next sunrise、每個可用區間的 start，以及 end-exclusive 顯示端（actual end 減一分鐘）逐一重新呼叫 `calculateTrueSolarTime()` 後格式化為真太陽 HH:mm。這避免把 query correction 套用到整天事件，也保留既有 `07:00–08:59` 類型的 end-exclusive 文字習慣；actual `Date`／epoch 欄位不會被 display model 覆寫。watch 的 summary、rangeText 與黑黃道登貴標記維持原有文字 contract，true-solar summary 則使用同一模式的 display model。

若 true-solar context、solar events、DST transition、極區日出／日落或 boundary inversion 不可用，登貴只顯示 unavailable／無標記，不 fallback 到手錶結果，也不呼叫 `clearJinhanYujing()` 清除金函核心。solar-event cache 以 event date、座標、offset 與既有 fixed-offset calculator input 為 key，避免同一日每秒重算；本包沒有新增 timer、clock component、canvas、SVG、storage、dependency 或資料 schema。DST transition 仍維持 adapter 的 unsupported contract；奇門遁甲仍是 Hard Stop。

未來若要提供左手錶／右真太陽的雙圓形時鐘，這裡只記錄為 UX idea，8B-5B 不實作雙時鐘或第二套 renderer。

## 30. 8B-5B-R1 登貴 true-solar runtime display blocking bug 修正

8B-5B 的純 formatter 與 display model 在真實 `solar_terms_1899_2101.json`、`calculateSolarEvents()`、`calculateTrueSolarTime()` fixture 上均能把同一個 actual sunrise／sunset instant 轉成不同的手錶／真太陽鐘面；問題不在天文事件 instant、真太陽公式或 `chartClockDisplay.js`。原 runtime 仍可能在同一個 `latestBaziRenderRequestId` 由 lightweight 與 full-render 兩條入口建立等價 Jinhan snapshot，後到的 core-only DOM writer 會把已完成的 GuiDeng display 裝飾清回 null；原有 generation guard 只辨識 request id，沒有消除這種同 generation 重複 writer，也沒有在最後 commit 再確認 display model 的 mode。

## 31. 8B-5B-R2 登貴 watch／true-solar 共用正式 location 的 solar-event authority

8B-5B-R2 將正式排盤的 `location` 與 `watch`／`true-solar` clock mode 明確拆成兩個獨立維度。Source A 已設定的 `trueSolarTimeLocation` 是正式位置 authority；建立 watch `ChartTimeContext` 供正式登貴 runtime 使用時，會把這份 immutable location snapshot 明確放入 `context.location`。true-solar context 原本即帶同一份位置。於是同一筆上方查詢時間、同一 civil date、同一正式座標下，兩種模式的 sunrise、sunset、next sunrise actual instants 完全相同；模式差異只留在日／時柱 authority、23:00 有效日、登貴 rule branch 與顯示鐘面。

### 32.3 逐項結果與 blocking findings

#### 頂部正式排盤、picker 與有效日

#datetime 是上方唯一 formal query input；true-solar mode 仍以同一筆 watch/civil query instant 建立 context，並以 true-solar local parts 供四柱日／時 authority。月曆的 selectedCalendarDate 不是單純 query civil date：getSelectedCalendarDateFromDateTime() 在 watch local hour >=23 時加一天，所以它更接近本工具既有的「有效日」概念。renderMonthCalendarDays() 的格子則仍按 visibleCalendarYear/Month/day 建立，solar-term label 用 raw asia_taipei 日欄位，lunar label 用 CWA Taiwan civil date。因而在 true-solar 跨 23:00 時，四柱有效日、月曆 selected date、節氣日標籤與農曆可以同時不同；這不是計算錯誤，但目前 UI 沒有把四種語意說清楚。

十二時辰的顯示文字、selected state、current-now highlight、click action 必須分開看。現在申 15 ~ 17 的 click 仍用 buildDateTimeValueFromDateAndChineseHour() 把 #datetime 寫成 watch 15:00:00；真太陽 mode 下究竟要代表 A「手錶 15:00」或 B「真太陽 15:00 對應的 actual instant」是 Decision Required，不能由 audit 自行選擇。

#### 四柱節氣與七十二候（blocking audit）

目前 active true-solar path：

    renderTrueSolarBaziResult(result, context)
      └─ renderSeasonInfo(result, context.civil.timeZone)
           ├─ formatTermDateTime(currentTerm, Asia/Taipei)
           ├─ formatHouRangeDateTime(currentHou.start/end, Asia/Taipei)
           └─ formatTermDateTime(nextTerm, Asia/Taipei)

因此真太陽模式的目前節氣、下一節氣、目前候區間目前都顯示 legal civil Asia/Taipei（UTC+08），不是 dynamic IANA，也不是 true-solar local。currentHou.start/end 不是任意文字：src/seventyTwoHou.js 先以目前節氣到下一節氣的 actual-instant interval 三等分，保存 start/end ISO instant，再由 main formatter 轉成顯示。active renderSeasonInfo() 會列目前候的中／日名稱及目前區間，也列下一候名稱；沒有列下一候的 start/end 區間（legacy renderCurrentHou() 並非 active path）。

節氣日 panel 另由 renderSolarTermDayPanel() 以 formatSolarTermDateTime(term) 直接讀 asia_taipei，固定輸出 Asia/Taipei 的 MM/DD HH:mm。更嚴重的是 renderResult() 會更新該 panel，而 renderTrueSolarBaziResult() 只更新 season info、pillar extra 與 weekday，沒有更新或清空該 panel；切換到正式 true-solar 後它可能保留上一個 watch render 的內容。這是 BLOCKING FINDING（render lifecycle + authority 未對齊），本包只記錄。

節氣顯示有兩個合法候選，不能混成第三種：

1. 方案 1：true-solar presentation。節氣仍以 astronomical actual instant 決定年／月與先後，僅將同一 instant 轉成目前 mode 的 true-solar local clock。優點是符合真太陽 mode 排盤區鐘面一致；缺點是傳統曆書使用者可能不認得，且跨 23:00 的日期標籤更容易與 CWA／月曆不同。
2. 方案 2：legal/civil presentation。節氣維持 Asia/Taipei 或明確 IANA civil clock，強調這是傳統曆書資料表達；優點是避免誤以為節氣 instant 被改變、與現有資料來源相容；缺點是看起來違反整頁 true-solar 原則，必須把法定／曆書時間標籤說清楚。

本 audit recommendation：計算 authority 永遠保留 actual instant；在產品決策前維持現有 civil formatter 不做半套替換，但把 row 10–13 標成 blocking/decision，下一包一次定義 label、日期歸屬與 true/civil companion。不得只改 HH:mm 而不處理節氣日 panel、候區間與跨日語意。

#### 金函、登貴、飛星與奇門

8B-5B/R2 後，金函 current hour、黑／黃道表與 GuiDeng 都由 active mode snapshot 產生。黑／黃道表的 23:00–00:59、01:00–02:59 等文字本身是時辰 branch 的 semantic label；true-solar mode 以 true context 決定目前哪一格與標記，不需把靜態 label 重寫成一堆 correction 後的字串。GuiDeng 則不同：sunrise、sunset、下一次 sunrise 與每個 range endpoint 都以 actual instant 保存，chartClockDisplay.js 在 watch 用 IANA civil、true 用 calculateTrueSolarTime() 重算鐘面；這四項是 DONE。

#### 真太陽 tab、status 與 comparison exceptions

Source A 是上方排盤時間（臺灣 Asia/Taipei UTC+8）並標示「正式排盤來源」；Source B 是裝置目前時間與 dynamic IANA；Source C 是自訂當地日期／時間與 IANA，B/C 均標「僅換算查詢」。結果區刻意同列手錶時間、平太陽時、真太陽時、timezone、offset 與 correction；太陽事件區刻意顯示事件日期、地點、timezone、offset、日出／中天／日落。這個 tab 的產品角色是比較／換算工具，TYPE C comparison UI exception，不能因全頁排盤 mode=true-solar 而強迫只留下 true-solar。

### 32.4 最大的三個時間語意混用風險

## 35. 8B-6D Chinese-hour picker active-clock semantics

8B-6D 正式區分兩種輸入 authority。唯一正式排盤欄位 `#datetime` 永遠是 Asia/Taipei watch/civil local datetime；使用者直接編輯「精確排盤時間」時也仍是 civil semantics。十二時辰按鈕則是 active chart clock shortcut：watch mode 點申時直接選 civil 15:00:00；true-solar mode 點申時代表 target true-solar wall clock 15:00:00，必須先反解 actual instant，再把該 instant 的 Asia/Taipei civil clock 寫回 `#datetime`。true-solar wall clock 從不當成 Date 或 instant，也沒有新增第二份 formal datetime state。

### 35.1 單一 inversion authority

中立 pure module `src/trueSolarClock.js` 現在提供 `resolveTrueSolarLocalDateTimeToInstant()`。輸入為 target true-solar local parts、IANA timeZone、location 與可選 initial instant；每次 probe 都取得該 actual instant 的 IANA offset，再呼叫既有 `calculateTrueSolarTime()` reverse-check。solver 預設最多 12 次、hard cap 32 次、搜尋距離 hard cap 48 小時，沒有 network 或 timer；輸出為 status、instantMs、civil/true local parts、errorSeconds 與 iteration count，不把 Date 存進正式 context。

原 GuiDeng business adapter 保留原 public wrapper 與 DST-transition unsupported contract，但迭代演算法已移除，改為呼叫同一個中立 solver；GuiDeng 的 mapping、solar events、range inversion、actual instant 與 presentation contract 未改，因此 repo 只剩一份 true-solar wall-clock inversion algorithm。

Picker 將 solver 結果 round 至 civil second，再以共用 chart-clock formatter reverse-check。通常採 nearest second；若 nearest second 落在 requested Chinese-hour start 的前一個 fractional second，則向後推一秒，以免 23:00 target 被分類為亥時。最終誤差仍必須在 target ±1 second；否則視為 unsupported，不改 `#datetime`，只顯示「真太陽時辰目前無法換算。」且不清空既有盤。

### 35.2 effective day、selected 與 current

子時沿用既有 `buildDateTimeValueFromDateAndChineseHour()` effective-day contract：selected effective day D 點子時，target true-solar wall clock 是 D-1 日 23:00:00；其他時辰例如申時則是 D 當日 15:00:00。反解 civil date 可能與 target／effective day 不同，因此成功後仍保留使用者選定的 `selectedCalendarDate`，不以 resolved civil date 覆寫命理有效日。

## 37. 8B-FIX-1 Formal / Query Location Isolation

8B Final Completion Audit 發現共用座標 input 的 state ownership 仍未隔離：Source B/C 操作座標時可能清除或改寫 Source A 的 `trueSolarTimeLocation`，並連帶 invalidate 或重建正式真太陽盤。8B-FIX-1 只修正 `main.js` orchestration 與 regression；沒有修改 ChartTimeContext schema、Bazi／Flying／Jinhan／GuiDeng／Qimen core、真太陽時／solver／solar-events 公式、節氣、七十二候或農曆。

### 37.1 Location owners

* Source A 是唯一 formal location owner。既有 `trueSolarTimeLocation` 保留為正式座標，供 `currentTrueSolarChartContext`、正式 Bazi、Flying、Jinhan、GuiDeng、astronomical display 與 Chinese-hour picker inversion 使用。
* Source B（device）與 Source C（custom）各自保存獨立 query-location snapshot，只供該來源的真太陽換算與 solar-events comparison。B/C 的時間、時區、DST 選擇與座標都不寫入 formal context。
* 一組共用 DOM coordinate input 只是目前 source snapshot 的 editor／presentation。切換 source 時載入該 source 的 snapshot；DOM value 本身不是 authority。B/C 第一次啟用時可複製當時 formal location 作為獨立初始值，之後互不覆寫。

### 37.2 Input、calculate、geolocation 與 clear contract

座標 input/change/calculate/geolocation 都先擷取 active source，再只寫該 source owner。Source A 變更會沿用既有正式重建流程；Source B/C 即使輸入暫時 invalid，也只清自己的 query location/result，不清 formal location、不 invalidate `currentTrueSolarChartContext`，且不重跑正式 Bazi、Flying、Jinhan、GuiDeng、picker 或 `#datetime`。非同步 geolocation callback 使用操作開始時的 source snapshot，避免使用者等待期間切換 radio 後把結果寫到另一個 owner。

`clearTrueSolarTimePresentation({ clearFormalChart: false })` 是 B/C 的 query-presentation reset；正式 context 清除只保留給 Source A formal input 或 chart display mode lifecycle。Source A → B/C 不清 formal location，B/C → A 會恢復原 formal snapshot 與 coordinate input 顯示。

### 37.3 Explicit calculation location

`resolveTrueSolarTimeCalculation()` 與 query solar-events renderer 現在接收明確 `location`，不再暗讀 formal global。Source A 傳 formal location；Source B/C 傳各自 query snapshot。正式 GuiDeng 的 solar events 與 cache key仍使用 formal context location，B/C comparison 使用 query location且 cache key含座標，不會覆寫正式事件。Chinese-hour picker inversion仍只傳 `currentTrueSolarChartContext.location`。
